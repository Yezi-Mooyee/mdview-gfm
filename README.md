A featherweight Markdown viewer built on **GitHub's own renderer**.

> The application itself is called **mdview** — that is the name in the window title
> and on the command line. The repository is `mdview-gfm` only so it is easier to find.

- **GUI** — a native window, not a browser tab. Toolbar, recent files, light/dark themes, zoom, drag & drop.
- **CLI** — one command turns a Markdown file into HTML and hands it to your browser.

It renders with [github/cmark-gfm](https://github.com/github/cmark-gfm) — the parser that *defines* the GFM specification — and styles it with GitHub's official [github-markdown-css](https://github.com/sindresorhus/github-markdown-css). This is not "GitHub-like styling": it is the same parser and the same stylesheet.

## Why it exists

Every other "GitHub-style" Markdown viewer out there (MarkText, Obsidian, Typora, browser extensions…) actually renders with markdown-it, marked or goldmark, and only copies the *look*. This one uses the real thing, so tables, task lists, footnotes, strikethrough, autolinks and raw HTML behave exactly as they do on GitHub.

## Highlights

- **Genuinely tiny.** A few dozen KB of Python source, two runtime dependencies, no build step, no framework.
- **Smooth in daily use.** Scrolling long documents, switching files, changing themes and zooming are all instant — verified on a low-power, HiDPI tablet-class machine. The only slow part is the window appearing (see [Startup time](#startup-time)), which is a WebView2 runtime cost, not ours.
- **Portable / green software.** No installer, no registry writes, no `PATH` surgery. Put the folder anywhere and run it; delete the folder and it is gone. See [Where your data lives](#where-your-data-lives).
- **HiDPI done properly.** DPI awareness is declared before any window is created, so text stays crisp at 200% scaling instead of being bitmap-stretched.
- **Bilingual docs, English first.** This file is the primary one; [中文版在这里](README.zh-CN.md).

## Quick start

### 1. Requirements

| | |
|:--|:--|
| OS | Windows 10 / 11 (the GUI is built on Edge WebView2) |
| Python | 3.8 or newer |

### 2. Install the two dependencies

```powershell
python -m pip install pycmarkgfm pywebview
```

`pycmarkgfm` (142 KB wheel) is needed by both the GUI and the CLI. `pywebview` is only needed by the GUI — if you just want the CLI, `pip install pycmarkgfm` is enough.

If you keep the four `.py`/`.pyw`/`.cmd` files next to the three `github-markdown-*.css` files, you're done. Nothing to build.

### 3. Run the GUI

Double-click **`mdview-gui.pyw`**. The `.pyw` extension means Windows runs it with `pythonw`, so no console window flashes.

From a terminal:

```powershell
.\mdview-gui.cmd                  # empty window, pick a file from the toolbar
.\mdview-gui.cmd README.md        # open a file directly
```

You can also drag a `.md` file onto `mdview-gui.pyw` — or onto the window once it's open.

### 4. Run the CLI

```powershell
.\mdview.cmd README.md                 # render and open in your default browser
python mdview.py README.md --no-open   # just produce the HTML, print its path
type notes.md | python mdview.py -     # read from stdin
```

| Option | Effect |
|:-------|:-------|
| `--out PATH` | Where to write the HTML (default: `%TEMP%\mdview\`) |
| `--no-open` | Generate only, don't open a browser |
| `--safe` | Fall back to cmark-gfm's strict filtering (raw HTML escaped) |
| `--css PATH` | Use a different stylesheet |
| `--title TEXT` | Set the page title |

## Where your data lives

There is no install step and nothing is hidden inside the project folder. Everything the program writes goes to three places outside it:

| Path | What |
|:-----|:-----|
| `%APPDATA%\mdview\config.json` | Theme, zoom level, recent files |
| `%APPDATA%\mdview\webview\` | Edge WebView2 profile cache (GUI only) |
| `%TEMP%\mdview\` | Generated HTML for the CLI and the "open in browser" button |

Delete those three and you are back to a pristine state; delete the project folder and the program is uninstalled. The config file is read as `utf-8-sig`, so it tolerates a BOM if you edit it in Notepad.

## Interface

| Control | What it does | Shortcut |
|:--------|:-------------|:---------|
| ← / → | Back / forward through visited documents | `Alt+←` / `Alt+→` |
| Home | Return to the welcome page. Pushed as a *new* history entry, so Back still returns to the document you were reading | `Alt+Home` |
| Open… | File picker | `Ctrl+O` |
| Reload | Re-read the current file from disk (keeps your scroll position) | `F5` |
| Browser | Open the same rendered result in your default browser | `Ctrl+B` |
| − / + | Zoom 70%–200% | `Ctrl+-` / `Ctrl+=` |
| Auto / Light / Dark | Theme; Auto follows the system | — |

A few behaviours worth knowing:

- **Drag & drop a file onto the window** to open it. WebView2 swallows external drops itself and does not pass them to the parent window (turning off `AllowExternalDrop` only makes it *refuse* them — the cursor turns into a no-entry sign), so this goes through WebView2's official file channel instead: the page hands the `File` objects to the host, which reads the real path. The loading happens on a background thread, because drag-drop callbacks run on the UI thread and waiting for JavaScript there deadlocks the window *and* the source Explorer window.
- **Only the left mouse button triggers links.** Middle and right click do not open anything (right click still shows WebView2's own context menu). Links never navigate inside the window — that would replace the whole GUI with the target page and leave you no way back. Local Markdown links switch the document in place, web links go to your browser, anything else goes to its default program.
- **Hovering a link** shows its target in the status bar at the bottom; local files are shown as Windows paths rather than `file://` URLs.
- **Recent files** are re-read from disk every time you enter the home page, and entries that no longer exist are dropped. Two instances running side by side therefore see each other's files, and saving merges with what is already on disk instead of clobbering it.
- **History stack** is capped at 100 entries, never records the same page twice in a row, and discards the forward branch when you open something new from the middle.
- **Theme switching** swaps between the three official stylesheets via the `media` attribute rather than `disabled`. `media="not all"` stylesheets are still downloaded, so the new one is already in memory when you switch — no window where the old styles are gone and the new ones are still loading, which is what used to make scrolling and layout jump.

## HiDPI

Handled explicitly, because getting it wrong makes everything blurry:

- **DPI awareness is declared before any window is created** (`SetProcessDpiAwareness(2)`). Without it the process is treated as DPI-unaware and the whole WebView is bitmap-stretched — visibly soft at 200% scaling.
- **Window size is computed from the screen's *logical* resolution** and handed to pywebview, which converts to physical pixels. On a 2736×1824 @200% display (logical 1368×912) the window opens at roughly 1180×820 logical pixels — most of the screen without overflowing.
- Page content uses CSS pixels, so WebView2 renders it crisply at whatever device pixel ratio applies.

## Startup time

The window appears, then the content follows a moment later. That gap is the Edge WebView2 runtime initialising, and it has nothing to do with document size — a page containing a single `<h1>` measured *slower* than a full document. Our own code accounts for about 1.3 s (declaring DPI, loading pythonnet/CLR, creating the window); the remaining 6–20 s is WebView2, and it varies wildly with system load.

Passing `--disable-features=msSmartScreenProtection` and similar flags to WebView2 was tried and made no measurable difference, so no flags are used.

Once the window is up, everything is instant.

## About Edge WebView2

The GUI renders through the **Microsoft Edge WebView2 Runtime**. It is a system component, not a browser you have to use:

- It ships with Windows 11 and is present on essentially every up-to-date Windows 10 machine.
- You do **not** have to use the Edge browser, and you do not have to keep it around. What matters is the WebView2 *Runtime*.
- If it happens to be missing, install the Evergreen Runtime from Microsoft: <https://developer.microsoft.com/microsoft-edge/webview2/>

The CLI does not need WebView2 at all — it just writes an HTML file and asks your browser to open it.

## How it differs from github.com

The renderer is identical, but GitHub runs some post-processing on top that this does not:

- **Syntax highlighting** — GitHub colors code server-side with Highlight.js; here you get the `<pre lang="...">` structure but no colors.
- **Emoji shortcodes** — GitHub turns `:smile:` into 😄; here it stays as written.
- **Heading anchors** — GitHub gives every heading an `id` for anchor links; here there are none.
